## Feature 1 — Restore ArrowLeft/ArrowRight bar-navigation hotkeys

**Symptom:** in the shipped app, ArrowLeft/ArrowRight do nothing. They used
to seek one bar back/forward.

**Root cause (confirmed via `git log --follow -p -- ui/src/App.tsx`):**
there are two parallel hotkey systems — native (`app/platform/MacKeyMonitor.mm`
→ `MainComponent::matchAndPerformAction()`, `app/MainComponent.cpp:153-214`,
driven by `ActionCatalogue::kActionIds` in `app/ActionCatalogue.h:22-37` and
`AppSettings.keybindings`) and a JS fallback in `ui/src/App.tsx`'s
`useGlobalHotkeys` (lines 57-193). The JS fallback still contains full
ArrowLeft/ArrowRight bar-seek logic (lines 116-137: `barSec = (60/bpm) *
tsNum`, then `transport.seek()` to the bar boundary), but commit `dc121c7`
("feat: add native action support for undo, redo, and stop-to-start with
key stroke tracking") wrapped that whole block in `if (!IS_EMBEDDED)`
(line 75) under the stale assumption that native now handles all key
bindings — but arrow-seek was never actually added to the native side.
`IS_EMBEDDED` (`ui/src/lib/embedded.ts:8`) is true whenever the page runs
inside the packaged app's WKWebView, i.e. always true in production, so the
JS fallback is dead in the shipped app and there is no native replacement.

**Fix:** add real native bar-seek, don't just unwrap the JS gate (unwrapping
would only fix the bare-browser-tab case, not the packaged app, which is
the actual product).

1. Add two new action ids to `ActionCatalogue::kActionIds`
   (`app/ActionCatalogue.h:22-37`), matching the existing naming style
   (`section_prev`/`section_next`): `bar_prev`, `bar_next`.
2. Give them default key bindings (ArrowLeft → `bar_prev`, ArrowRight →
   `bar_next`) in whatever sets `AppSettings`' default `keybindings` map —
   find where `section_prev`/`section_next`/etc. get their defaults seeded
   (`app/AppSettings.cpp` or `app/MainComponent.cpp` init) and add these two
   alongside, so a fresh install has them out of the box, and existing
   installs (through your own settings.json) can add/rebind them via the
   existing Settings → "Keyboard & MIDI shortcuts" UI without any new UI
   work (`BindingRow` in `SettingsScreen.tsx` already generically renders
   whatever's in `ActionCatalogue::kActionIds`).
3. Implement the actual seek in `MainComponent::matchAndPerformAction()`
   (or wherever `performAction()` dispatches action ids,
   `app/MainComponent.cpp`) for `bar_prev`/`bar_next`: needs current BPM,
   time-signature numerator, and playhead position, all already available
   from `engine.project()`/the current song/transport state (the JS math
   this needs to mirror: `barSec = (60/bpm) * tsNum`; snap current position
   down to the nearest bar boundary, then step one bar further in the
   requested direction — not just "current position ± barSec", so repeated
   presses stay bar-aligned even if the playhead is mid-bar when the first
   press happens). Call the engine's existing seek entry point (same one
   `next`/`prev`/section actions or the transport-seek REST handler use).
4. Extract the bar-boundary math into a small **pure, testable function**
   rather than inlining it — a natural home is a new tiny header in
   `engine/timing/` (pure, no JUCE dependency, consistent with how
   `engine/` is kept platform-independent and tested). Cover it with a
   doctest `TEST_CASE` in `/tests` (e.g. `test_bar_seek.cpp`): odd
   time signatures (3/4, 7/8), fractional BPM, seeking prev from exactly on
   a bar boundary (should go to the *previous* bar, not stay put — standard
   DAW behavior), seeking prev/next near time 0.
5. Leave the JS fallback in `ui/src/App.tsx` alone (still correct for the
   bare-browser-tab, non-embedded case) — just make sure it doesn't
   double-fire when native also handles it (it won't, since it's gated on
   `!IS_EMBEDDED` and native only runs when embedded).
6. Optional/nice-to-have, not required: expose `bar_prev`/`bar_next` in the
   native Transport menu (`MacMenuBar.mm`) next to Section Prev/Next, since
   that menu already mirrors the transport action set 1:1.
7. This feature is also the natural first consumer of Feature 3 (menu-bar
   flash-on-trigger) if that's built first — otherwise it's fine standalone
   and Feature 3 picks it up automatically later since it flashes on
   *any* action id.

## Feature 2 — Recent projects tracking

**Current state:** nothing exists — no JUCE `RecentlyOpenedFilesList`, no
frontend MRU list. Fully greenfield (`app/MainComponent.cpp:1143-1290` has
new/open/save/save-as handlers with no recent-list bookkeeping anywhere).

**Design:**

- Store the MRU list **rig-wide**, not per-project, in `AppSettings`
  (`app/AppSettings.h`/`.cpp`, same file already responsible for
  `keybindings` and persisted to
  `~/Library/Application Support/ResoStage/settings.json`). Add e.g.
  `std::vector<RecentProjectEntry> recentProjects;` where an entry is at
  least `{ path (string), displayName (string), lastOpenedIso (string) }`.
  Cap at a reasonable N (10 is a sane default — don't overthink it).
- Update the list on every successful project **load** and **save**
  (`MainComponent::loadProjectFromPath` success path, and
  `saveProjectClicked` success path, `app/MainComponent.cpp:~1175-1290`):
  add-or-move-to-front, dedupe by path, cap at N. **Extract this
  add/dedupe/cap logic as a small pure function** (not inlined) so it's
  unit-testable without needing a JUCE-linked test target — put it
  somewhere plain-C++ (could live in `engine/` if truly platform-agnostic,
  or as a header-only free function in `app/` if it needs to stay app-side;
  prefer `engine/` if it doesn't need any app-only types). Cover with a
  doctest case: adding a duplicate path moves it to front instead of
  duplicating, list caps at N and evicts oldest, order is most-recent-first.
- Handle stale entries: if opening a recent entry fails (file
  moved/deleted), don't crash — surface the existing load-failure UX and
  drop or gray out that entry rather than leaving a dead shortcut. Decide
  the exact UX (silently drop vs. show disabled/greyed with a "missing"
  hint) at implementation time — either is fine, just be consistent between
  native menu and web UI.
- **Native surface:** add an "Open Recent" submenu under File in
  `app/platform/MacMenuBar.mm` (which currently has no Recent Files
  submenu at all), rebuilt whenever the list changes (mirror how
  `updateMacMenuUndoRedo()`/`updateMacMenuKeyBindings()` already do
  event-driven menu rebuilds from `MainComponent`).
- **Web surface:** extend `ProjectMenu` in `ui/src/App.tsx` (lines
  494-622) with a "Recent" list/submenu next to New/Load/Save/Save As.
  Recent-project data needs to reach the frontend — either push it as part
  of `WebUiState` (like `lastAction`/`lastActionNonce` already do for other
  rig-wide state) or add a small dedicated settings-read endpoint next to
  the existing `settings.*` helpers in `ui/src/lib/api.ts`. Prefer piggy-backing
  on the existing settings read/write path since recent-projects is
  conceptually part of `AppSettings`, not per-tick transport state — don't
  bloat the 30Hz `WebUiState` payload with something that only changes on
  project open/save.
- Non-embedded (bare browser tab) fallback: recent projects backed by
  native file paths don't make sense in a browser tab (no filesystem
  access model matches the native one — browser flow already uses
  `<input type=file>`/upload per `ProjectMenu`'s non-embedded branch). Skip
  showing Recent in the non-embedded UI, or show it read-only/disabled —
  don't invent a parallel browser-side recent list, that's solving a
  problem nobody has.

## Feature 3 — Flash/highlight a hotkey's trigger in the menu bar

**Existing reusable primitive:** every action firing (hotkey, MIDI, or menu
bar itself) already bumps `WebUiState.lastAction` /
`WebUiState.lastActionNonce` (`app/web/WebServer.h:220-224`,
`ui/src/lib/types.ts:241-245`). The web Settings screen already consumes
this: `BindingRow` in `SettingsScreen.tsx` (lines 123-221, specifically
155-169) flashes a small accent dot for 500ms when its own action's nonce
changes. **Reuse this exact mechanism and timing (500ms)** — don't invent a
second notification channel.

**What's actually new here is the native menu bar itself flashing**, since
`MacMenuBar.mm` currently has no live feedback at all beyond the existing
Undo/Redo title/enabled sync. Cocoa `NSMenu`/`NSMenuItem` doesn't support
arbitrary flashing/re-coloring while closed (the menu bar title itself is
just static text until opened) — the standard, idiomatic way to give a
transient visual acknowledgement on a *closed* top-level `NSMenu`/
`NSMenuItem` is a brief checkmark/state toggle (`NSMenuItem.state =
.on`) applied to the specific item whose action id just fired, cleared
after ~350-500ms via a `juce::Timer` (match the existing 500ms web timing
for consistency), mirroring how `updateMacMenuUndoRedo()` already mutates
item state reactively. Implement as `MacMenuBar::flashAction(const
juce::String& actionId)`: look up the `NSMenuItem`(s) whose
`representedObject` matches `actionId` (menu items already carry action ids
per the existing routing design), toggle state on, start/restart a timer
that clears it. Wire this to fire from the same central dispatch point
every action already passes through (wherever `lastActionNonce` gets
bumped natively, or `MainComponent::performAction()`/
`matchAndPerformAction()` — whichever is the true single choke point for
"an action just fired" natively), so it covers hotkeys, MIDI, and clicking
the menu item itself uniformly, per the user's ask ("когда какой-то хоткей
отрабатывает — подсвечивай это в меню баре").
- Only View/Transport/Edit menu items map cleanly to action ids today —
  that's fine, those are exactly the ones driven by hotkeys.
- This is native Cocoa UI feedback; don't invent a fake unit test for
  "does the checkmark toggle" — that's a manual/QA-verified behavior, not
  meaningfully unit-testable. If the add/clear scheduling logic ends up
  factored into something pure and reusable, fine to test *that* in
  isolation, but don't force it.

   memory) — do not guess glyph class names, check fontaudio's own

2. The existing build pipeline needs **no backend changes** for this:

4. Replace usages:
   - `MetronomeIcon` in `PlayerScreen.tsx` → `<FontIcon name="metronome"/>`

5. No new test framework needed for this feature alone — it's presentation

## Feature 5 — Ensure playhead is in view when switching to Player/Editor

**Current state:** `PlayerScreen.tsx` (mounts `<Timeline>` at line 777) and
`EditorScreen.tsx` (mounts its own separate `<Timeline>` instance inside its
"Timeline" sub-tab, line 1173) each own **independent** scroll/zoom/gesture
state inside `Timeline.tsx` (3,979 lines, single largest frontend file —
see the multi-writer-discipline warning below, this file has had **7
consecutive stability-fix commits** in the days leading up to this plan,
most recently `5c8e550`/`356bd70`/`9e56d6a`/`13538ff`/`e20a2d5`, fixing
exactly the kind of scroll/zoom/gesture races a careless new feature could
reintroduce). Switching tabs today does not reposition either instance's
scroll — whatever it was left at (or its default) is what's shown.

**Before implementing, verify:** whether HeroUI's `Tabs` unmounts hidden
panels or keeps them mounted-but-hidden via CSS. This determines the
trigger mechanism (a mount effect is enough if unmounted; if kept mounted,
need an explicit "just became active" signal instead, e.g. an `isActive`
prop threaded down from `App.tsx`'s `tab` state, or the `sendView`
call site).

**Plan:**

1. Thread an `isActive`-equivalent signal into each `<Timeline>` instance:
   `PlayerScreen` is active when `App.tsx`'s `tab === "player"`;
   `EditorScreen`'s Timeline sub-view is active when `tab === "editor"`
   **and** its own internal sub-tab is `"timeline"` (`EditorScreen.tsx`'s
   own `TABS` array, ~1102-1108) — don't fire the reveal when Editor is
   open but on Songs/Tracks/Events/Busses.
2. On the transition into "active", check if the current playhead X
   position falls within the visible scroll viewport ± a small margin; if
   not, do **one** programmatic scroll to bring it into view. **Reuse the
   existing single-writer scroll path** — there is already a `rAF`-driven
   glide used for auto-follow/song-transition easing (~line 2469) and a
   `programmaticScrollRef` (line 1667) that marks self-triggered scroll
   writes so they aren't misread as user gestures; call into that same
   glide function rather than writing `scrollLeft` from a new location.
   Introducing a second, independent writer of `scrollLeft` is exactly
   what the recent stability-fix commits were about preventing — **do not
   do this as a fire-and-forget `element.scrollLeft = x` from a brand new
   effect**, route it through the established mechanism.
3. This should be a one-shot "ensure visible on switch", not continuous
   following — don't fight `followMode` (off/snap/smooth), which governs
   continuous auto-follow during playback and is a separate, already
   user-configurable behavior. If the playhead is already visible when you
   switch tabs, do nothing.
4. **Worth a real test:** extract the "is X within viewport ± margin"
   check into a small pure function (e.g. `isPositionVisible(scrollLeft,
   viewportWidth, playheadX, margin)`), and this is the point where
   introducing **Vitest** for the frontend earns its keep — cover boundary
   cases (exactly at each edge, just inside/outside with margin, fully
   off-screen in each direction, zoomed far in vs. far out). This is real,
   non-trivial logic (off-by-one-prone), unlike Feature 4's pure wiring —
   worth testing, unlike that one.

## Feature 6 — Dual-mode (Audio / Light) timeline, ResoLight simulator, 3D fixture placement editor

This is the large one. **Deliberately scoped into phases** — the research
document pasted into the original request describes a multi-quarter
professional lighting-console product (grandMA3-style tracking engine,
automation-envelope view, phaser/movement engine, palettes, full DMX
fixture personalities); building all of it in one pass would be scope
creep against "don't design for hypothetical future requirements." Build
Phase A completely (it's what the user's concrete asks in points 6 map to:
dual-mode toggle, non-clickable cross-mode hint content, ResoLight config +
3D placement editor + simulator, project settings card), leave B/C
explicitly documented as future extensions, not started.

### Existing foundation (thin, not zero — `engine/audio/ArtNetPacket.{h,cpp}`,
`app/events/EventDispatcher.{h,cpp}`, `engine/project/ProjectSchema.h:70-106`
`TimelineEvent::EventType::Dmx`/`Http`): a working, tested (see
`tests/test_artnet_packet.cpp`) Art-Net ArtDMX packet builder/parser and an
off-audio-thread dispatcher that can fire a raw byte blob to a universe at
a timeline point or song load. **No fixture abstraction, no continuous/
automated light data, no "ResoLight" concept, no 3D anything exist yet** —
this batch is genuinely new territory built *on top of* that low-level
transport, not a replacement for it.

### Data model (new, in `engine/project/ProjectSchema.h` and `project.json`)

- `LightFixture`: `{ id, name, kind: "resolight_bar" | "dmx_generic", … }`.
  - `resolight_bar` kind: `{ gridColumn, gridRow, ledCount, addressable
    (bool), position3d: {x, y, z}, rotation3d? }`. The grid
    column/row is just *how many bars exist and their nominal
    arrangement* (per the user's ask: "кол-во вертикальных столбов и
    горизонтальных" = configure a grid of N columns × M rows of vertical
    bars); the actual `position3d` is set via the 3D editor and is
    independent of grid indices, since real stage placement is rarely a
    perfect uniform grid — grid count decides *how many fixtures exist and
    a sane default layout*, the 3D editor lets you move them precisely.
  - `dmx_generic` kind: `{ universe, startChannel, channelCount }` (reuses
    existing `ArtNetPacket`/`EventDispatcher` transport, no personality/
    profile system in Phase A — that's a Phase C concern).
- `LightTrack`: `{ id, name, fixtureIds: [...] }` — sits alongside audio
  tracks in the project, analogous structure.
- `LightCue`/light timeline block: `{ id, trackId, startSec, endSec (or
  durationSec), color: {r,g,b}, intensity: 0..1, fadeInSec, fadeOutSec,
  label }`. This is the MVP "Cue Block" visualization from the research doc
  — a discrete colored block with slanted fade edges — **not** the
  automation-envelope view, phaser engine, or tracking pseudo-line (those
  are Phase C, see below). Simple, matches what a two-bar ResoLight rig and
  a handful of generic DMX fixtures actually need day one.
- `LightingConfig` (project-level, lives in project settings, not rig-wide
  `AppSettings` — this is per-show data): `{ enabled: bool (default
  false), kind: "resolight" | "dmx_generic" | "none", resolight?: {
  columns: int, rows: int, bars: [LightFixture] } }`.
- **Worth real engine-side tests** (deterministic, pure math, exactly the
  kind of thing `tests/` is good at): 
  - ResoLight DMX channel-layout computation: given N bars each with
    `ledCount` and `addressable` flag, compute the channel map per
    universe (addressable = 3 channels/LED RGB typically; non-addressable
    = presumably one RGB triplet drives the whole bar — confirm this
    assumption against how ResoLight hardware actually addresses, since
    it's a real product the user owns, not a guess to lock in blindly).
  - Cue interpolation: given a sorted list of `LightCue`s on a track and a
    query time T, compute the resulting color+intensity (handles: before
    first cue, inside a fade-in/fade-out ramp, holding at full value
    between ramps, after last cue, overlapping-cue edge cases — decide and
    document the overlap-resolution rule, e.g. last-cue-wins or
    highest-priority-track-wins).
  Put both in a new `engine/lighting/` module (pure, JUCE-free, consistent
  with how `engine/` is kept testable-without-JUCE today), with doctest
  coverage in `/tests`.

### Timeline dual-mode UI (`ui/src/components/Timeline.tsx`, Editor's
instance primarily — Player's Timeline is a performance/monitoring view,
not an authoring surface, so it's reasonable to leave it audio-only and
scope the mode toggle to Editor's Timeline; revisit only if the owner
actually wants light cues visible during live performance, which is a
product question, not an implementation detail, so don't assume it)

- Add a segmented Audio/Light mode toggle to the Timeline toolbar,
  per-instance state, persisted the same way `followMode` already is
  (`localStorage`, e.g. `resostage.timeline.viewMode`).
- In Audio mode: light tracks (if any exist/enabled) render as a **dimmed,
  non-interactive** hint strip near the top — per the user's explicit ask
  ("для света... подсвечивай что мол есть но не кликабельное") — no click
  targets, just enough visual presence to know light content exists there.
  In Light mode: the reverse — a dimmed non-interactive waveform hint strip
